# Engine V2 synthetic geometric-kernel CPU qualification

This contract measures the real one-candidate full-Cartesian geometric
admission kernel. It generates deterministic synthetic binary64 coordinates;
it accepts no molecule, case, benchmark corpus, reservation, timer, callable,
host DTO, expected digest, or RSS override. It cannot authorize historical A/B,
Fresh-128, a public benchmark, a product claim, Stage 0, or molecular execution.

The canonical profile is
`config/engine_v2_cpu_performance_profile.json`. It is exact canonical JSON
with one trailing newline. Duplicate names, JSON floats, alternate ordering or
whitespace, input/output drift, threshold drift, and any true authority field
fail closed.

## Measured implementations

The timed baseline is the already-normalized `_evaluate_metrics` call used by
fixed64 for every generation-eligible candidate; batch input normalization and
receptor copying are outside that Python timing boundary. The public
`evaluate_geometric_admission_metrics_one_python` wrapper remains the bounded
parity/replay surface but is not timed. The optimized implementation is the
single-threaded PyO3
`geometric_admission_metrics_one` function in native package `0.2.0rc6`.
Both traverse every ligand-receptor pair in ligand-major/receptor-minor order;
neither uses a count-only proxy, spatial shortcut, fallback, or Rayon worker.
The native timing includes its PyO3 call and owned input copies, matching the
current candidate-level native integration cost and avoiding an inflated
Python baseline.

The native binding records and verifies the extension SHA-256, Rust source and
Cargo.lock SHA-256, the native `pyproject.toml`, Rust compiler, target, release flags, Python interpreter,
Python geometric source, performance-runner and qualification-bootstrap
sources, clean Git commit, and the native build receipt. The native build
embeds Cargo.lock, `Cargo.toml`, `pyproject.toml`, `build.rs`, the build wrapper,
and `src/lib.rs` identities. Qualification evidence records byte-identical
wheel builds from the digest-pinned manylinux image with a read-only source
mount; the runtime contract binds the installed extension, package metadata,
and complete installed-file manifests rather than persisting a wheel-file
SHA-256. Cargo/linker/maturin identities
outside those recorded fields are not separately claimed as a portable build
attestation. The runtime projection also
rehashes every non-bytecode file under the exact NumPy and `numpy.libs`
payloads, the complete installed Python 3.10 standard library, and the actual
loaded shared-library closure. Count, total bytes, and canonical manifest
SHA-256 are frozen in the profile; added, missing, changed, linked, or escaped
NumPy payloads fail closed.

The runtime-payload manifest and the installed-distribution manifest are
separate evidence. The latter parses all 918 exact NumPy `RECORD` rows, verifies
the hash and size of all 917 present files (including the real `bin/f2py`),
requires the sole installer-generated bytecode row to be typed-absent, and
requires exact set equality with every file under `numpy`, `numpy.libs`, and
`numpy-1.26.4.dist-info`. `RECORD` itself, installer markers, metadata, and the
console script are therefore covered without pretending that they are timed
kernel inputs. The site-packages top-level inventory remains exact: only NumPy,
`numpy.libs`, the native package, and their two dist-info directories may
exist.

## Frozen inputs and parity

| Fixture | Ligand atoms | Receptor atoms | Exact pairs |
| --- | ---: | ---: | ---: |
| small | 16 | 512 | 8,192 |
| medium | 32 | 2,048 | 65,536 |
| large | 48 | 4,096 | 196,608 |

Every artifact stores each complete input once as canonical binary64
hexadecimal coordinates, radii, heavy-atom mask, pocket center, and pocket
radius. Sentinels cover coincident/contained overlap, tangency, partial
overlap, heavy and non-heavy penetration, non-overlap, and pocket escape.
Count-preserving coordinate changes therefore change the frozen input receipt.

Atom/pair/penetration counts and the accept/reject decision require exact
parity. The five floating metrics use the predeclared field-specific rule
`absolute difference <= tolerance OR ULP distance <= limit`. Timing begins
only after parity-capable exact input views and both implementations are
loaded. The Python expected output SHA-256 is frozen for every fixture; native
rows preserve their complete metric payload and output SHA-256.

## Authoritative local lane

- CPU model: `AMD Ryzen 9 5900X 12-Core Processor`
- boost: disabled
- child affinity: exactly logical CPU `2`
- OMP, Rayon, OpenBLAS, MKL, BLIS, NumExpr and vecLib threads: `1`
- OS task count before, during parent polling, and after the kernel: `1`
- warmups: `5` per role and fixture
- samples: `30` per role and fixture
- order: paired alternating `AB/BA`
- percentile: integer nearest-rank p95
- timers: `perf_counter_ns` and `process_time_ns`
- isolation: a new process for every role observation
- interpreter: exact CPython `3.10.12` from a clean virtual environment with
  `include-system-site-packages=false`
- interpreter flags: exact `-I -S -B`; environment variables are ignored,
  bytecode writes are disabled, and randomized hashing remains enabled
- import order: frozen standard-library roots first, then the repository and
  the single qualified site-packages root; package initializers are not run
- the first CPython path, `/usr/lib/python310.zip`, is required absent before
  any non-built-in bootstrap import and is rechecked in every runtime binding
- the three repository modules are bounded-read and compiled directly from
  their owner-controlled source files; import cache bytecode is never used
- customization: no empty import path, `sitecustomize`, `usercustomize`, or
  pre-existing NumPy bytecode cache
- the complete host execution context is read before and after all observations;
  CPU model, boost state, affinity, platform, byte order, parent identity, and
  parent task count drift discards the complete measurement

Each child receipt binds the run nonce, global ordinal, phase, pair index,
role, PID/PPID/start ticks, entry/pre/post affinity, task count, controlled
thread environment, wall and process-CPU arithmetic, input SHA before/after,
complete output, exact pair count, and explicit false fallback/molecular flags.
It also binds the effective interpreter flags, complete import path, bootstrap
path roles, runtime manifests before and after the timed call, and absence of
customization modules. `PYTHONHASHSEED` is deliberately not claimed: `-I`
implies environment isolation, so the receipt records effective randomized
hashing rather than an ignored environment value.
Child output and total duration are bounded; timeout kills the child process
group. Peak RSS is captured by both child and parent, including warmups, but is
descriptive only because it is not a sufficiently portable optimization gate.

The medium and large fixtures each require at least `1.5x` p95 wall-time
speedup. The small fixture may regress by at most `5%`. Decisions use integer
cross multiplication, and all parity rows must pass. A threshold miss is
`NO_GO`; an unqualified host, dirty source tree, missing/mismatched native
binding, incomplete transcript, or timeout is `BLOCKED`, not a result.

## Successor profile v3 host preflight

Profile v3 has a new profile and schema identity. It binds the terminal v2
record and rederives hashes for the unchanged fixtures, kernel, parity,
sampling, runtime, and numerical gates. Its only admitted semantic change is
the Linux sysfs boost-state reader.

Linux sysfs pseudo-files may report a page-sized `st_size` while returning only
the short current value. The v3 reader therefore treats reported size as
advisory and bounds bytes actually read to 32. It still requires the exact
`/sys/devices/system/cpu/cpufreq/boost` path, `O_NOFOLLOW`, a root-owned regular
file, one link, no group/world write bit, stable descriptor/path identity, and
two identical bounded reads of one of the exact payloads `0`, `0\n`, `1`, or
`1\n`.

The v3 command below is read-only and non-consuming. It launches no timed
measurement, writes no evidence artifact, reserves nothing, accepts no
molecular input, and grants no execution or claim authority:

```bash
python3 tools/verify_engine_v2_cpu_performance_profile_v3.py
python3 tools/preflight_engine_v2_cpu_performance_v3.py
```

Passing this preflight only proves that the host contract can be read.

## Profile v3 runner activation

The separate v3 runner activation binds the v3 profile, terminal v2 record,
host reader, inherited v2 measurement core, runner, and verifier source. The
runner has no caller-supplied probe or fixture input. It reuses the unchanged
three synthetic fixtures and fixed 210-observation schedule, performs pre/post
host and source checks, discards partial measurements, and transactionally
publishes one owner-only absent-only artifact plus one terminal state.

The supported live API requires the artifact output path and validates that
path before it consumes anything. It then creates the fixed account-scoped
attempt marker with `O_EXCL` before host preflight or child launch. The state
directory is derived from the login account database, not `$HOME`, at
`.betelgeuze-engine-v2/qualification/<profile-sha256>/`. It is created and
opened component-by-component with owner-only permissions and no-follow
descriptors. A second process, thread, or supported direct caller therefore
cannot acquire another ordinal-one attempt for the same account and profile.

After measurement, the runner claims its opaque process-local result exactly
once, atomically publishes the artifact, replays it through the bounded
owner-only reader, and writes an absent-only terminal record. The terminal
record binds the exact attempt bytes and receipt, run nonce, output-path hash,
artifact bytes and receipt, decision, numeric outcome, blockers, and false
authority. Only after all three records reverify does the public API return a
`PersistedCPUPerformanceRunV3`, whose live capability and qualification
authority are false. If any step after attempt creation fails, the attempt
marker remains and no decision object is returned; recovery cannot rerun the
profile.

GitHub Actions may verify the activation and offline artifacts but is
explicitly denied live execution. The activation does not authorize molecular,
historical, Fresh-128, public benchmark, scientific-claim, or product-claim
work:

```bash
python3 tools/run_engine_v2_cpu_performance_qualification_v3.py \
  --verify-activation
```

This activation PR does not consume the exactly-once v3 profile attempt. A
subsequent approved clean exact-main operation may invoke `--run-output` once.
Live execution requires the exact CPython 3.10.12 virtual environment and the
stdlib-only `-I -S -B` bootstrap; a normal package import is not an equivalent
lane:

```bash
/approved/engine-v2-qualification-venv/bin/python -I -S -B \
  tools/run_engine_v2_cpu_performance_qualification_v3.py \
  --run-output /approved/local/path/geometric-cpu-qualification-v3.json
```

GitHub Actions is rejected both by the bootstrap and by the underlying runner
before state-directory creation. CI may only use `--verify-activation` and
offline `--verify-artifact`; the latter rejects symlinked, non-owner-only,
multi-link, or oversized inputs before parsing.

## Live versus offline evidence

The predecessor v2 `run_sealed_local_performance_runner()` API returned a
process-local `LiveCPUPerformanceRunResult`. Profile v3 retains an opaque live
object only as an internal handoff between the reserved executor and its
single-use writer; it is absent from the public export surface. The public v3
entry point returns only after artifact and terminal persistence. Neither the
internal registry nor the local attempt ledger is a cryptographic attestation,
and neither grants production, scientific, molecular, or external authority.

Persisted JSON explicitly records `offline_replay_only=true`,
`offline_artifact_gate_eligible=false`,
`live_run_capability_serialized=false`, and
`qualification_authority=false`. The offline loader returns a different type
whose live capability is always false. It never reads the current host or
joins the process-local live-result registry, even when an artifact records
`GO` and is replayed on the original machine. Canonical hashes and transcript
checks make an offline artifact structurally replayable, but unkeyed persisted
data can be fabricated and resealed. Offline replay therefore can never prove
that execution occurred and can never attest its host, timing, or native
implementation.

Artifacts are published absent-only with mode `0600`, a descriptor-anchored
no-follow staging file, file fsync, atomic no-clobber link publication, and
directory fsync. The parent inode is bound across validation/open, all path
components reject writable non-sticky ancestors, and the immediate parent must
be owned by the current UID and non-writable by group/other. Readers require a
single-link owner-only `0600` artifact. Existing files, symlink paths,
concurrent creation, parent replacement, and ambiguous link publication fail
closed. As with ordinary owner-controlled POSIX files, another malicious
process running as the same UID is inside this local trusted-parent boundary;
this file protocol is not a cryptographic or production execution attestation.

descriptive input to replay, not proof of an execution and not an admitted
qualification decision.
